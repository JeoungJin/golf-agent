# Feature Specification: 화면 구조 개편 · 이름 입력/수정 · 응답 속도

**Feature Branch**: `003-ux-nickname-performance`

**Created**: 2026-10-27

**Status**: Draft (US1~US3은 구현 완료 후 사후 문서화, US4~US5는 미구현)

**Input**: User description: "UI/UX 전면 수정: 공지사항/스크린/필드를 따로 조회하고 '모두 보기'는 없앤다. 지난 일정과 예정 일정을 확실히 구분하고, 로그아웃 버튼은 본인 이름 옆에 둔다. 공지사항/스크린/필드 버튼은 항상 화면 상단에 있어야 한다. 목록이 여러 건이면 행 바탕색을 달리하고, 수정·상세 화면에도 바탕색을 준다. 라운딩 등록 시 종류 초기값이 설정되어야 한다. 현재 속도가 느린 편이다. 카카오 가입 후 별명이 없는 사람은 '회원'으로 가입되므로, 별명이 없는 사람은 이름을 입력하게 하고 이름은 수정할 수 있어야 한다."

> 이 스펙은 002의 "홈 다음 라운딩 카드"(FR-017)를 대체하고 001의 홈 대시보드를 폐기한다. 상세는 하단 "다른 스펙과의 관계" 참고.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 항상 보이는 상단 메뉴와 종류별 조회 (Priority: P1) — 구현됨

승인된 회원은 어느 화면에서든 상단에서 본인 이름, 로그아웃, 그리고 **공지사항 / 스크린 / 필드** 메뉴를 본다. 메뉴를 누르면 해당 종류의 목록만 보인다. "전체 보기"는 없다.

**Why this priority**: 모든 화면의 이동 기준이므로 가장 먼저 정해져야 한다.

**Independent Test**: 로그인 후 어느 화면에서든 세 메뉴가 같은 위치에 보이고, 각 메뉴가 해당 목록만 보여 주며, 스크롤해도 상단에 고정되는지로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 승인된 회원, **When** 어느 화면이든 열면(상세·등록·수정 포함), **Then** 상단에 이름, 이름 바로 옆 로그아웃 버튼, 공지사항/스크린/필드 메뉴가 보인다.
2. **Given** 긴 목록, **When** 아래로 스크롤하면, **Then** 이름 줄과 메뉴는 화면 상단에 고정되어 있다.
3. **Given** 현재 화면이 스크린 목록, **When** 메뉴를 보면, **Then** "스크린"만 강조(현재 위치)되어 있다.
4. **Given** 홈(`/`) 접속, **When** 화면이 열리면, **Then** 공지사항 목록이 표시된다.
5. **Given** 종류가 없는 라운딩 목록 주소(`/rounds`), **When** 열면, **Then** 스크린 목록으로 이동한다.
6. **Given** 매니저, **When** 상단을 보면, **Then** "가입신청 목록" 버튼도 보이며, 공지 작성은 공지사항 목록에서, 라운딩 등록은 해당 종류 목록에서 시작한다. 멤버에게는 이 버튼들이 없다.

---

### User Story 2 - 지난 일정과 예정 일정의 확실한 구분 (Priority: P1) — 구현됨

라운딩 목록에서 예정 라운딩과 지난 라운딩이 한눈에 구분된다. 목록이 여러 건이면 행마다 바탕색이 달라 줄을 구별하기 쉽다.

**Why this priority**: 지난 일정을 예정으로 착각하면 투표·참석 실수로 이어진다.

**Independent Test**: 예정·지난 라운딩이 섞인 목록에서 두 구역이 색·제목·배지로 구별되고, 예정 행이 여러 색으로 번갈아 보이는지로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 예정·지난 라운딩, **When** 목록을 보면, **Then** 예정 구역은 "예정 라운딩" 제목과 컬러 행, 지난 구역은 "지난 라운딩 (종료)" 제목과 점선 회색 박스, 각 지난 항목에 "종료" 배지가 보이고 흑백 처리된다.
2. **Given** 예정 라운딩이 여러 건, **When** 목록을 보면, **Then** 행 바탕색이 하늘·연두·노랑·분홍·보라 순으로 반복된다. 공지 목록은 두 가지 회색이 번갈아 나온다.
3. **Given** 취소된 라운딩, **When** 목록을 보면, **Then** "취소됨" 배지로 지난 라운딩의 "종료"와 구별된다.
4. **Given** 어두운 화면 모드, **When** 목록을 보면, **Then** 같은 구분이 어두운 색으로 유지된다.

### User Story 3 - 입력·상세 화면의 바탕색과 등록 초기값 (Priority: P2) — 구현됨

등록·수정 폼과 상세 화면은 바탕색이 있는 카드 안에 표시되어 구역이 구분된다. 라운딩 등록 화면은 종류가 미리 선택되어 있다.

**Why this priority**: 입력 실수를 줄이고 화면 구조를 분명히 하지만, 핵심 동작에는 영향이 없다.

**Independent Test**: 스크린/필드 목록에서 각각 "라운딩 등록"을 눌러 종류가 해당 값으로 선택되어 열리는지, 폼·상세가 카드로 구분되는지로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 스크린(또는 필드) 목록, **When** "라운딩 등록"을 누르면, **Then** 종류가 스크린(또는 필드)으로 선택된 채 열린다. 종류 정보 없이 열면 스크린이 기본이다.
2. **Given** 라운딩·공지의 등록·수정 화면, **When** 열면, **Then** 입력 전체가 연한 바탕색 카드에 담기고 입력칸은 흰색으로 구분된다.
3. **Given** 공지/라운딩 상세, **When** 열면, **Then** 정보 영역이 바탕색 카드로 구분되고, 투표 현황·내 투표·인원 요약은 서로 다른 바탕색으로 구분된다.

### User Story 4 - 별명이 없는 회원은 이름을 입력하고 언제든 수정 (Priority: P1) — 미구현

카카오 계정에서 닉네임을 받지 못해 "회원"으로 가입된 사람은 첫 로그인 직후 이름을 입력해야 앱을 쓸 수 있다. 모든 회원은 이후에도 자기 이름을 고칠 수 있다.

**Why this priority**: 이름이 모두 "회원"이면 매니저가 가입 신청을, 회원들이 투표 명단을 구분할 수 없다. 그룹 운영의 기본 전제다.

**Independent Test**: 닉네임 없이 카카오로 가입한 계정이 이름 입력 화면에서 막히고, 입력 후 앱을 쓸 수 있으며, 이후 이름을 고쳐 명단·헤더에 반영되는지로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 카카오에서 닉네임을 받지 못한 신규 가입자, **When** 첫 로그인을 마치면, **Then** 이름 입력 화면이 먼저 열리고, 이름을 입력하기 전에는 다른 화면(승인 대기 안내 포함)으로 이동할 수 없다.
2. **Given** 이름 입력 화면, **When** 앞뒤 공백을 뺀 1~20자의 이름을 저장하면, **Then** 원래 가려던 화면(승인 대기 안내 또는 홈)으로 이동하고, 헤더와 가입 신청 목록에 입력한 이름이 보인다.
3. **Given** 빈 값이거나 공백뿐이거나 21자 이상, **When** 저장하면, **Then** 저장되지 않고 한국어 오류 안내가 보인다.
4. **Given** 카카오에서 닉네임을 받은 회원, **When** 가입하면, **Then** 이름 입력 없이 바로 진행되고 그 닉네임이 이름이 된다.
5. **Given** 로그인한 회원, **When** 헤더의 본인 이름을 누르면, **Then** 이름 수정 화면이 열리고 현재 이름이 채워져 있다. 저장하면 이후 명단·헤더·가입 신청 목록에 새 이름이 보인다.
6. **Given** 이미 "회원"이라는 이름으로 가입해 있던 기존 회원, **When** 다음에 접속하면, **Then** 이름 입력 화면이 열린다.
7. **Given** 승인 대기 중인 회원, **When** 이름을 입력·수정하면, **Then** 저장된다(매니저가 승인 전에 실명을 확인할 수 있다). 거절된 회원은 이름을 수정할 수 없다.
8. **Given** 다른 회원, **When** 타인의 이름을 바꾸려고 직접 요청해도, **Then** 거부된다.

### User Story 5 - 빠른 화면 응답 (Priority: P1) — 부분 구현

회원이 메뉴를 누르거나 저장했을 때 화면이 기다림 없이 반응한다. 저장이 성공했는데 "실패" 안내가 먼저 뜨는 일이 없다.

**Why this priority**: 체감이 느려 저장 결과를 오해한 사례가 이미 보고됐다.

**Independent Test**: 서울 지역 사용자 기준으로 주요 화면의 서버 응답 시간을 측정해 목표 안에 드는지, 저장 직후 성공 화면으로 이동하는지로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 서버와 DB가 같은 지역에 있을 때, **When** 공지 목록·라운딩 목록·상세를 열면, **Then** 서버 응답이 목표(SC-001) 안에 든다.
2. **Given** 로그인 상태, **When** 한 화면을 한 번 열면, **Then** 인증 확인과 회원 정보 조회가 요청당 각각 한 번을 넘지 않는다.
3. **Given** 느린 네트워크, **When** 화면이 로딩 중이면, **Then** 빈 화면 대신 로딩 표시가 보인다.
4. **Given** 등록·수정·삭제 저장, **When** 처리가 성공하면, **Then** "실패" 안내는 보이지 않고 결과 화면으로 이동한다.

---

### Edge Cases

- 카카오에서 닉네임 대신 다른 이름 필드만 온 경우: 있는 값 중 첫 번째를 이름으로 쓰고, 하나도 없을 때만 이름 입력을 요구한다.
- 이름 입력 도중 로그아웃은 가능해야 한다(입력 화면에서도 상단의 로그아웃 사용).
- 이름 입력 화면에서 새로고침하거나 다른 주소로 직접 이동해도 이름 입력 전까지는 다시 이 화면으로 돌아온다.
- 동명이인: 같은 이름을 허용한다(구분은 매니저가 승인 시 확인). 구분이 필요하면 후속 기능.
- 이름 앞뒤 공백은 제거하고, 내부의 연속 공백은 그대로 둔다.
- 매우 긴 이름이나 공백 없는 문자열이 헤더·명단에서 화면 폭을 넘지 않는다(360px).
- 지난 라운딩만 있는 종류: "예정된 라운딩이 없습니다"와 지난 구역이 함께 보인다.
- 메뉴 항목 중 하나도 현재 위치가 아닌 화면(상세·등록 등)에서는 어느 메뉴도 강조되지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 로그인한 회원에게 모든 화면 상단에 본인 이름, 이름 바로 옆의 로그아웃, 공지사항/스크린/필드 메뉴를 고정 표시해야 한다.
- **FR-002**: 공지사항, 스크린, 필드는 각각 따로 조회해야 하며 "전체 보기" 화면이나 버튼을 제공하지 않는다. 종류가 지정되지 않은 라운딩 목록 접근은 스크린으로 보낸다.
- **FR-003**: 홈(`/`)은 공지사항 목록으로 이동해야 한다.
- **FR-004**: 현재 위치에 해당하는 메뉴를 강조해야 한다.
- **FR-005**: 라운딩 목록은 예정과 지난 라운딩을 제목·바탕·테두리·배지·흑백 처리로 구분해야 하며, 취소됨은 별도 배지로 구분해야 한다.
- **FR-006**: 예정 라운딩 행은 여러 색을 순환해 칠하고, 공지 행은 두 회색을 번갈아 칠해 행을 구별할 수 있어야 한다. 모든 색은 어두운 모드에서도 대응해야 한다.
- **FR-007**: 라운딩 등록 화면은 종류가 초기 선택되어야 한다(목록에서 보던 종류, 없으면 스크린).
- **FR-008**: 등록·수정 폼과 상세 화면은 바탕색 카드로 영역을 구분해야 하며 입력칸은 대비되어야 한다.
- **FR-009**: 시스템은 회원이 카카오에서 닉네임을 받지 못해 이름이 기본값으로 정해진 경우를 "이름 미설정"으로 구별해 기록해야 한다.
- **FR-010**: 이름 미설정 회원(승인 대기 포함, 거절 제외)이 로그인하면 이름을 입력하기 전까지 이름 입력 화면 외 모든 화면 접근을 막고 그 화면으로 보내야 한다. 로그아웃은 가능해야 한다.
- **FR-011**: 이름은 앞뒤 공백 제거 후 1~20자여야 하며, 위반 시 한국어 오류 안내와 함께 저장을 거부해야 한다. 같은 이름은 허용한다.
- **FR-012**: 회원은 본인 이름만 수정할 수 있어야 하며, 수정은 헤더의 본인 이름에서 진입한다. 타인의 이름을 바꾸는 시도는 화면 노출 여부와 관계없이 거부되어야 한다. 이름 저장은 서버(DB 함수)가 최종 검증한다.
- **FR-013**: 이름을 저장하면 헤더, 투표 명단, 가입 신청 목록 등 이름이 표시되는 모든 곳에 반영되어야 한다.
- **FR-014**: 이미 기본값 이름("회원")으로 가입한 기존 회원도 이름 미설정으로 간주해 FR-010을 적용해야 한다.
- **FR-015**: 서버 함수와 데이터베이스는 같은 지역에 있어야 하며, 한 요청에서 인증 확인과 회원 정보 조회가 각각 한 번을 넘지 않도록 해야 한다.
- **FR-016**: 데이터를 불러오는 동안 주요 화면(공지·라운딩 목록, 상세)은 로딩 표시를 보여야 한다.
- **FR-017**: 쓰기 작업(등록·수정·삭제·투표)이 성공했는데 오류 안내가 표시되어서는 안 된다.
- **FR-018**: 모든 화면은 360px 이상에서 가로 스크롤이 없어야 하며 한국어로 제공해야 한다. (002 FR-018 유지)

### Key Entities

- **회원(Member)**: 기존 개체. 이름(닉네임)과 함께 "이름이 설정되었는가"를 구별하는 상태를 가진다. 카카오 닉네임이 있으면 설정됨, 기본값이면 미설정에서 시작한다.

## Success Criteria *(mandatory)*

- **SC-001**: 서울 지역 사용자 기준, 공지 목록·라운딩 목록·라운딩 상세의 서버 응답 시간(콜드 스타트 제외)이 75퍼센타일 500ms 이내이고, 저장 동작(등록·수정·삭제·투표)이 사용자 눈에 2초 이내에 결과 화면으로 이어진다. 측정 방법은 plan의 "측정" 절에 정의한다. *(현재 기준값 미측정 — T-P01에서 먼저 측정)*
- **SC-002**: 이름이 설정되지 않은 회원이 이름 입력 없이 앱의 다른 화면을 볼 수 있는 경우가 0건이다.
- **SC-003**: 신규 가입자의 100%가 첫 로그인 후 이름 입력(필요 시)을 포함해 1분 이내에 승인 대기 또는 홈 화면에 도달한다.
- **SC-004**: 타인의 이름을 바꾸는 데 성공하는 경우가 0건이다.
- **SC-005**: 저장이 성공했는데 "실패" 안내가 표시되는 경우가 0건이다.
- **SC-006**: 어떤 화면에서든 상단 메뉴 세 항목이 첫 화면(스크롤 없이)에 보인다.
- **SC-007**: 360px·414px 폭의 주요 화면(상단 메뉴, 목록, 상세, 등록·수정, 이름 입력)에서 가로 스크롤이 0건이다.

## 다른 스펙과의 관계

- **002 FR-017(홈 다음 라운딩 카드)**: 폐기. FR-001~FR-003이 대체한다.
- **001 홈 대시보드(US2)**: 홈이 공지사항 목록으로 대체되어 폐기. 가장 가까운 라운딩 안내는 스크린/필드 목록의 "예정 라운딩" 구역이 맡는다.
- **001 FR-004(카카오 닉네임과 프로필 이미지만 저장)**: "카카오 닉네임 또는 회원이 직접 입력한 이름, 그리고 프로필 이미지"로 개정한다. 입력받는 것은 이름 하나뿐이라 개인정보 최소 수집(헌법 V)을 해치지 않는다.
- **001 Edge Case(닉네임 동의 안 함 → 기본 닉네임 "회원")**: 기본값으로 계속 진행하는 대신 이름 입력을 요구하도록 개정한다.
